## 演習

- 第1回（素のLLM）とエージェントの回答の違い：
  同じ質問「AIE2026の講座の宿題にある『3レベル』とは何ですか？」で比べたところ、app.ask は講座のことを知らず、「初級・中級・上級」「AI活用レベル」など一般論を2通り推測し、資料の確認を勧めて終了した。app.agent は用語集（homework-levels）を検索し、「基礎・実装・発展の3段階で、どれか1つで完了、原則採点しない」と定義どおりに答え、最後に「関係する回：第1回」を付け加えた。

- `--trace` で見えたツール呼び出し（ツール名と引数）：
  質問「LoRAとQLoRAの違いは？」で、`search_glossary({'query': 'LoRA'})` と `search_glossary({'query': 'QLoRA'})` の2回呼び出した。docstring の「query には調べたい用語を1つだけ入れる」に従い、用語ごとに別々に検索した。

- 1つの質問での LLM 呼び出し回数（`requests`）：
  `requests=2, tool_calls=2`。1回目の呼び出しで2つの検索を並列に依頼し、2回目で検索結果を使って回答を生成した。

- 追加したツールと、docstring に書いた説明：
  - ツール：`make_quiz(lecture: int)`。指定した回の用語を1つ選び、問題と答えを JSON で返す。
  - docstring：「指定した回の用語から1つを選び、確認問題と答えを返す。『第2回の確認問題を出して』のように、復習用の問題を求められたときに使う。lecture には回の番号を整数で入れる。返り値は question と answer を含む JSON。利用者が答えるまで answer は見せない。」
  - 結果：「第2回の内容から確認問題を1問出して」で `make_quiz({'lecture': 2})` が呼ばれ（`requests=2, tool_calls=1`）、「過学習」の問題が出題された。ツールは答えも返したが、モデルは docstring に従って答えを伏せて出題した。
  - テスト：存在しない回（lecture=0）を指定すると用語が0個になり、そのままでは `random.choice` がエラーになるため、「用語が見つからない」というメッセージを返すようにした。`uv run pytest -q` で11件のテストがすべて通った（11 passed）。
  

## 宿題

- 取り組んだレベル：基礎、実装、発展（a）（b）
- 4課題とも演習で作ったエージェント（同じ `INSTRUCTIONS` と3つのツール）を出発点にした。

### 基礎：INSTRUCTIONS・docstring を1か所ずつ変えて比較

ねらい：`INSTRUCTIONS` やツールの docstring を1か所ずつ書き換え、同じ質問を `--trace` 付きで実行して、ツールの呼ばれ方や回答がどう変わるかを比べる。

- 比較の基準（変更なし）：
  「LoRAとQLoRAの違いは？」と聞くと、変更前は次のように動いた。
  - `search_glossary('LoRA')` と `search_glossary('QLoRA')` で2回検索
  - `requests=2, tool_calls=2`（LLMを2回呼び、ツールを2回使った）
  - 回答の最後に「関係する回：第2回」

- 実験1：`search_glossary` の docstring「query には調べたい用語を1つだけ入れる」を「まとめて入れる（例: "LoRA QLoRA"）」に変更
  - 結果：`search_glossary({'query': 'LoRA QLoRA'})` の1回にまとまった（`tool_calls` 2→1、`requests` は2のまま）。ツールを直接呼ぶと、まとめたクエリでも LoRA・QLoRA の両方の定義が返っており、回答の内容は同等だった。
  - 気づき：docstring の例が、そのまま引数の形に反映された。このツールは部分一致で複数語を拾えるので「1つずつ」は必須ではなかったが、完全一致の検索などではまとめると取りこぼす可能性がある。

- 実験2：`INSTRUCTIONS` から「必ず search_glossary で用語集を確認する」の行を削除
  - 結果：「3レベル」でも「LoRAとQLoRA」でも、削除前と同じように検索してから答えた。
  - 気づき：`search_glossary` の docstring にも「答える前に使うこと」と書いてあり、指示が2か所に重なっていたため、片方を消しても効果が残った。末尾の回の表記は「（関連回：第1回）」「（第2回）」のように揺れた。

- 実験3：`INSTRUCTIONS` の「回答の最後に、関係する回（第N回）を示す」を「回答の最後に、内容の理解を確かめる確認問題を1問出す」に変更
  - 結果：「関係する回」の行が消え、末尾に確認問題が付いた（出力トークン 167→256）。ただし `make_quiz` は呼ばれず、モデルが検索結果から自分で問題を作った。
  - 気づき：指示にツール名が無く、`make_quiz` は回の番号からランダムに用語を選ぶ作りなので、質問の話題に合った問題を出すにはモデルが自分で書くほうを選んだと考えられる。ツールを使わせたいなら、指示にツール名と使う場面を書く必要がある。


### 実装：承認付きの save_learning_log

ねらい：学習の記録をファイルに保存するツールを作る。実行する前に利用者の承認（y/N）を求める。

- やったこと：
  - ツールを作った：`app/tools.py` に `save_learning_log(title, content)` を追加した。`learning_log/` フォルダに「日時_題名.md」というファイル名で保存する。
  - 承認が必要なツールとして登録した：`app/agent.py` で `requires_approval=True` を付けて登録した。モデルがこのツールを呼ぼうとした時点で実行がいったん止まる。
  - 止まったときの結果を受け取れるようにした：`output_type` に `DeferredToolRequests`（承認待ちのツール呼び出しの一覧）を加えた。
  - 承認の画面を作った：CLI で、承認待ちのツール名と引数（title・content）を表示し、`[y/N]` で聞くようにした。
  - 答えを渡して再開するようにした：利用者が y/N に答えたあと、y なら許可、n なら `ToolDenied`（拒否）を `DeferredToolResults` に入れる。その後、y でも n でも、止まるまでの会話の履歴（`message_history`）と一緒に渡して、止まったところから実行を再開する。

- 結果：
  - 最初の版では、承認の確認が出なかった。
    - trace（ツール呼び出しの記録）を見ると、`save_learning_log` は一度も呼ばれていなかった。
    - 代わりに、モデルが回答の最後で「学習ログに保存しますか？」と、会話の中で自分で聞いて終わっていた。
    - 原因：docstring に「実行の前に利用者の承認を求める」と書いたため、モデルが「承認は自分が会話で取るもの」と解釈したと考えられる。
  - docstring と `INSTRUCTIONS` を書き換えた：「確認はプログラムが自動で行うので、会話で確認を求めずに直接ツールを呼ぶ」。
    - すると、`[approval] save_learning_log …` と表示されて実行が止まり、保存しようとしている title と content が表示された。
  - y（承認）の場合：質問「LoRAとQLoRAの違いを調べて、要点を学習ログに保存して」
    - `learning_log/20261103-064610_LoRAとQLoRAの違い.md` が保存された。
    - モデルは「保存しました」と伝えて回答を終えた。
  - n（拒否）の場合：質問「過学習とは何か調べて、学習ログに保存して」
    - 再開後、モデルには、ツールの結果として「利用者が実行を許可しませんでした。」が返った。
    - ファイルは作られなかった。
    - モデルは過学習の説明だけを返して終わった。

- 気づき・疑問：
  - 承認の仕組みを用意しても、docstring の一文で、モデルが自分で確認する方向に流れ、ツールを呼ばなくなった。基礎の実験と同じく、説明文がふるまいを左右する。
  - 使用量の表示（`[usage]`）は、実行1回分しか数えない。
    - 再開後の表示は requests=1（y なら保存の結果、n なら拒否の知らせを見て回答した分）。
    - 止まる前の実行で requests=2（検索 → 保存の依頼）を使っている。
    - 合わせると、y でも n でも、実際は LLM を計3回呼んでいる。
  - 拒否したとき、モデルは「保存しなかった」ことに触れなかった。利用者には保存されたかどうかが分からない。`ToolDenied` のメッセージに「保存しなかったことを利用者に伝える」と書き足せば改善できると思われる。


### 発展（a）：ADK で作り直す

ねらい：演習のエージェントと同じ指示とツールを使い、エージェントを組み立てる部分だけを Google の ADK（Agent Development Kit）で書き直す。書き方と回答を、演習の Pydantic AI 版と比べる。

- やったこと：
  - `adk_agent/glossary_agent/` フォルダに、`agent.py` と `__init__.py` を作った。
  - 演習と同じ `INSTRUCTIONS` と3つのツール（`search_glossary`・`get_lecture_summary`・`make_quiz`）を、ADK の `Agent` に渡した。
  - `PYTHONPATH=. uv run --with google-adk adk run adk_agent/glossary_agent` で起動した（モデルは gemini-3.5-flash-lite）。
  - 演習と同じ3つの質問を投げて、回答を比べた。

- 結果：
  - 「3レベル」：基礎・実装・発展のどれか1つで完了、原則採点しない、関係する回：第1回。Pydantic AI 版とほぼ同じ回答。
  - 「LoRAとQLoRAの違い」：用語集の定義に沿った説明で、関係する回：第2回。こちらも同等。
  - 「第2回の確認問題」：「事前学習」の意味を問う問題を出し、答えは伏せた。
    - 演習では「過学習」だった。`make_quiz` は `random.choice` で用語を選ぶので、毎回変わる。
  - 書き方の違い：
    - Pydantic AI：`Agent(instructions=...)` でエージェントを作ってから、`agent.tool_plain(関数)` でツールを1つずつ登録する。実行は自前の CLI（`app/agent.py`）から `run_sync` で行う。
    - ADK：`Agent(name=..., model=..., instruction=..., tools=[関数, ...])` と、指示もツールも作るときにまとめて渡す。`root_agent` という変数名と `__init__.py` の決まりに従っておけば、`adk run` がエージェントを見つけて、対話用の CLI を用意してくれる。
    - 共通点：どちらも、関数の docstring と型ヒント（`lecture: int` など）から、ツールの説明を自動で作ってモデルに渡す。

- 気づき・疑問：
  - 指示とツールの docstring が同じなら、フレームワークを変えても、回答やふるまいはほぼ変わらなかった。ふるまいを決めているのは、フレームワークより指示と docstring のようである。
  - `adk run` は、会話の履歴を保ったまま続く対話形式だった。
    - 1問ごとに終わる `app.agent` とは異なる。
    - 途中で誤って入力した文も、履歴に残る。
  - `adk run` には、`--trace` のようにツール呼び出しを表示する機能がない。そこで、`adk web`（ブラウザで開く開発用の画面）で確かめた。
    - Events（実行の記録）に、`search_glossary("LoRA")` と `search_glossary("QLoRA")` が1回の応答で並列に呼ばれ、その結果を受けて回答が作られる流れが表示された。
    - 演習の Pydantic AI 版（requests=2, tool_calls=2）と同じ呼ばれ方だった。
    

### 発展（b）：Pi を Codespaces で動かし、システムプロンプトを比較する

ねらい：コーディングエージェントの Pi を動かし、Pi のシステムプロンプト（モデルに最初に渡す指示文）と、自分のエージェントの `INSTRUCTIONS` を比べる。

- やったこと：
  - `npm install -g --ignore-scripts @earendil-works/pi-coding-agent` で Pi を入れた。
  - `pi --model gemini-3.1-flash-lite` で起動し、「app/tools.py を読んで、どんなツールが定義されているか説明して」と聞いた。
  - インストール先の `dist/core/system-prompt.js` を読み、システムプロンプトの組み立て方を、自分の `INSTRUCTIONS` と比べた。

- 結果：
  - 動作：
    - 起動時に、ファイル検索用のツール（fd・ripgrep）を、利用者に確認せず自分でダウンロードした。
    - 質問に対して、`read app/tools.py:1-2000`（ファイルの読み込み）を確認なしで実行し、`save_learning_log` を含む4つのツールを正しく説明した（入力 約4.1k トークン、出力 403 トークン）。
  - システムプロンプトの作り：
    - Pi のシステムプロンプトは、決まった1つの文章ではなく、部品をタグで区切って組み立てる作りだった。
    - 部品は、preamble（役割）・tools（ツールの一覧と説明）・rules（ツールの構成に応じた規則と、「簡潔に」「ファイルのパスを示す」などの出力の規則）・docs（Pi 自身の説明書の場所）・project_context（AGENTS.md などプロジェクトの指示の差し込み）・skills・cwd（今の作業フォルダ）。
  - 自分の `INSTRUCTIONS` との比較：
    - Pi にあって、自分の `INSTRUCTIONS` に無いもの：
      - 本文の中のツール一覧
      - 作業フォルダやプロジェクトの指示などの、環境の情報
      - 出力の一般的な規則
      - ツールの構成や拡張によって変わる、可変の組み立て
    - 自分の `INSTRUCTIONS` にあって、Pi に無いもの：
      - 用語集に無いことは断定しない、という根拠の規則
      - 答える前に必ず調べる、という順序
      - 最後に関係する回を示す、という形式
      - 宿題の答えを書かない、という教育上の制約
    - どちらにも無いもの：利用者に確認を求める規則。Pi は確認なしで動き、自分のエージェントは確認を `requires_approval=True`（プログラムの仕組み）で行っている。

- 気づき・疑問：
  - Pi は、どの作業にも使えるように、環境の情報や一般的な規則を厚く持つ。自分のエージェントは、用語集の質問に答える用途に絞り、根拠や形式の規則を持つ。汎用のエージェントと、用途を絞ったエージェントの違いが、システムプロンプトにそのまま表れていた。
  - 実装の宿題では、docstring に「承認を求める」と書くと、モデルが会話で聞いてしまい、ツールを呼ばなくなった。プロンプトに書いた確認はモデルの解釈に左右されるので、安全のための確認は、`requires_approval=True` のような仕組みで担うほうが確実だと考えられる。Pi のように確認の規則を持たないエージェントを使うときも、この点に注意が必要だと思われる。
