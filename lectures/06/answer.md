### 実装：make_quiz を MCP で公開し、範囲外を扱う

- やったこと：
  - `app/tools.py` に `make_quiz(lecture: int)` を追加し、`app/mcp_server.py` で公開した（ツール名は `glossary_make_quiz`）。
  - 範囲外を2種類に分け、どちらも JSON で `error`・`available_lectures`・`hint` を返すようにした。
    - 回の番号として不正（0 以下）。
    - 番号は正しいが、用語集にその回の用語がない（第5回、第99回）。
  - `tests/test_tools.py` に正常系と範囲外のテストを2つ追加した（23 passed）。
- 結果：
  - [tool call]：`glossary_make_quiz({'lecture': 99})`。
  - [tool return]：`{"error": "第99回の用語は用語集にないため、確認問題を作れません。", "available_lectures": [1, 2, 3, 4, 6], "hint": "…どの回にするか利用者に確認してください。"}`。
  - Gemini は別の回で勝手に作らず、作れる回（第1〜4回・第6回）を示して「どの回の問題をご希望ですか？」と聞き返した。モデル応答は2回。
  - 比較のため、`make_quiz` を一時的に書き換え、第99回のときに例外を投げる方式も Gemini で試した（試したあと `git restore` で戻した）。

    | 方式 | trace の表示 | モデルが受け取った内容 | Gemini の回答 |
    |---|---|---|---|
    | 文字列で返す（採用） | `[tool return]` | 自分で書いた JSON がそのまま届く | 第1〜4回・第6回を示して聞き返した |
    | `ValueError` を投げる | `[tool error]` | `Error executing tool make_quiz` だけ。日本語のメッセージはサーバーの ERROR ログにだけ出た | 「第1回〜第N回など」とぼかして聞き返した |
    | `ToolError` を投げる | `[tool error]` | `Error executing tool make_quiz: 第99回の用語は…作れる回: 1, 2, 3, 4, 6` が届いた。サーバーのログは INFO の1行 | 第1〜4回・第6回を示して聞き返した。別の回で呼び直してはいない | 
    
- 気づき・疑問：
  - MCP サーバーは、想定外の例外の中身をクライアントに渡さない。内部の情報を漏らさないための作りだと思うが、そのため `raise ValueError("…")` と丁寧に書いても、モデルには届かない。実際、`ValueError` のときの Gemini は作れる回が分からず、「第1回〜第N回など」とぼかして聞き返した。モデルに読ませたい失敗は、返り値で返すか `ToolError` を投げる必要がある。
  - `ToolError` でも、今回の Gemini は別の回で呼び直さず、聞き返した。返り値の方式と回答は変わらず、違いは trace とサーバーのログに「失敗」として残ること。利用者の判断が要る失敗（存在しない回）は返り値、呼び出し側の誤り（型の誤りなど）は `ToolError`、と使い分けるのがよさそうである。
  - `hint` の「どの回にするか利用者に確認してください。」という指示が効いているのかも確かめた。この一文だけを消し、「第99回のクイズを作って」を指示あり・なしで3回ずつ実行すると、どちらも3回とも作れる回を並べて聞き返し、別の回で呼び直すことはなかった（モデル応答は毎回2回）。聞き返したのは指示に従ったからではなく、作れる回の一覧という情報があったからだと考えられる。`ValueError` で一覧が届かなかったときに回答がぼやけたことと合わせると、範囲外のメッセージで大事なのは、モデルへの指示より、次にどうするかを決めるための情報を渡すことだと思う。

### 発展：Claude Code の MCP 設定と比べる

- 調べた日：2026-11-26
- 参照した公式ドキュメント：
  - https://code.claude.com/docs/en/mcp
  - https://code.claude.com/docs/en/mcp-quickstart
- やったこと：Claude Code の MCP サーバーの設定方法を公式ドキュメントで調べ、演習の `app/mcp_servers.json` と比べた。
- 結果：
  - 設定を書く場所
    - 演習：`app/mcp_servers.json` の1つだけ。
    - Claude Code：local（既定）は `~/.claude.json` の、そのプロジェクトの項目の下。project はプロジェクト直下の `.mcp.json`。user は `~/.claude.json`。`claude mcp add` コマンドでも書き込める。
    - 違い：演習は置き場所が1つ。Claude Code は置き場所が3つあり、コマンドでも登録できる。
  - コマンドで起動する書き方
    - 演習：`"command"` ＋ `"args"`。
    - Claude Code：同じ `"command"` ＋ `"args"`（＋`"env"`）。`type` がない項目は stdio として読まれる。コマンドなら `claude mcp add <名前> -- <コマンド> [引数…]`。
    - 違い：ほぼ同じ。外側の `"mcpServers"` の形も同じなので、`glossary` と `fetch` はそのまま `.mcp.json` に移せる。
  - URL で接続する書き方
    - 演習：`"url"` だけ。
    - Claude Code：`"type": "http"` ＋ `"url"`。`"headers"` で認証ヘッダーを付けられる。コマンドなら `claude mcp add --transport http <名前> <URL>`。
    - 違い：いちばん大きな違い。演習の `"aws": {"url": "…"}` をそのまま写すと、`type` がないので stdio として読まれ、設定の誤りになる。`"type": "http"` を足す必要がある。
  - 有効になる範囲
    - 演習：このリポジトリのエージェントだけ。
    - Claude Code：local は自分だけ・このプロジェクトだけ。project は `.mcp.json` をコミットすれば、clone した全員。user は自分の全プロジェクト。同じ名前は local → project → user の順に優先される。
    - 違い：演習は範囲が1つだけ。Claude Code は、自分だけかチームで共有するかを選べる。
  - Claude Code には、演習にない仕組みもある。
    - 対話で使うときは、`.mcp.json` のサーバーを使う前に利用者の承認を求める（任意のプログラムを起動できるため）。
    - `${VAR}` で環境変数を展開できるので、API キーを設定ファイルに直接書かずに済む。
- 気づき・疑問：
  - 演習のエージェントは、`mcp_servers.json` に書かれたものを確認なしで起動・接続する。演習の補足（提供元とリスクを確認してから足す）を、利用者の注意に任せずに仕組みとして求めているのが Claude Code の承認だと理解した。演習の STEP 3 で fetch の説明文にモデルへの指示のような文があったことからも、この確認は大切だと思う。
  - ただし公式ドキュメントによると、承認を求めるのは対話で使うときだけで、`claude -p` のように自動で実行するときは、確認なしで `.mcp.json` のサーバーを読み込む。また、clone したリポジトリが、自分の設定ファイルで自分のサーバーを承認済みにしておくことはできない（信頼していないフォルダでは無視される）。承認の仕組みがあっても、自動で動かすときや、人のリポジトリを clone して動かすときは、演習のエージェントと同じく、設定ファイルの中身を自分で読んでから実行する必要がある。
