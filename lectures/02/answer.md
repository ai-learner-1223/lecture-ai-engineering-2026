- ファインチューニングが向く場面・向かない場面についての考察：
  - **向く場面：出力の形式・振る舞いを揃えたいとき。** 210 件・10 分の LoRA で、形式遵守率は 0.00 → 1.00 になった。検索で正しい定義を渡しても、学習前のモデルは JSON のキーを守れない（表 1 の base_rag は 0.09）。プロンプトの指示では守れない小さなモデルに、決まった形式で答えさせるのは学習の得意分野である。
  - **向かない場面：知識を入れ、正しく引き出させたいとき。** 学習と同じ聞き方なら定義を再生できたが、聞き方を変えると 2/12 まで落ちた。しかも外れたときは「知らない」と言わず、学習データの口調で、もっともらしい嘘を言い切る。用語集の更新のたびに再学習が必要になる点も含めて、知識は検索で渡すほうがよい。検索なら根拠の文がプロンプトに残るので、答えを確かめることもできる。
  - **「知らないと言う」判断はどちらでも保証されない。** 負例を学習させても、未知の語の半分以上を言い切った。検索は「何も引けなかった」ことは分かるが、名前の一部が重なる語（プロンプトインジェクション → プロンプト）では誤って引き、モデルはそれをもとに答えてしまう。判断を確実にするには、モデルに任せるのではなく、プログラム側で「検索が 0 件なら needs_review を true にする」といった規則を置く必要がある。
  - **検索側の限界も同じくらい大きい。** 名前を含まない逆引きの質問では何も引けず、B で検索が外れた 5 問は、どの条件でも 0/5 だった。学習でも検索でも解けない質問が残る。第3回のエージェントのように、モデルが検索語を言い換えて何度か検索する仕組みが必要になる。
  - **まとめ：形式は学習で、知識は検索で、判断は規則で担わせる。** 今回の 4 条件では、この分担に近い tuned_rag が最も良かった。ただし closed-book で学習したため、検索結果より学習の癖が優先される場面があった。組み合わせるなら、学習データ自体を「検索結果つきの入力 → 根拠に基づく答え」の形で作るのが次の改善点である。
